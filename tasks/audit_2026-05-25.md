## P1 — Importants

### Règles D&D 5e

- **Pas de tracking de proficiency par arme** — un Rogue qui équipe une Greataxe ajoute le proficiency bonus (faux). Ajouter un `weapon_proficiencies: list[WeaponCategory]` sur `Character`.
- **CHARMED** défini mais non implémenté (advantage du charmeur vs cible non appliqué).
- **CONCENTRATION** peut diverger : `combatant.spellcaster.concentration_spell` reste même si la condition `CONCENTRATING` est levée par les dégâts. Synchroniser dans `engine/conditions.py:remove_condition`.
- **SURPRISED** ne bloque pas les réactions (les opportunity attacks devraient être bloquées sur surprise).
- **TRUCE** mid-combat ne drop pas la concentration ([bot/combat_truce.py](bot/combat_truce.py)).
- **Pas de mécanique de cover** (half/three-quarters/full → bonus AC).
- **Pas de passive Perception** (utile pour stealth/sneak).

### Couche AI

- `ai/quest_generator.py:68-76` et `ai/npc_generator.py:84-85` : **pas de validation Pydantic** sur les outputs LLM (raw `.get()` coercion). Risque de payloads malformés acceptés silencieusement.
- `ai/narrator.py:47-89` : Tier-2 fallback supprime les sections mais le **system prompt continue à les référencer** → hallucination possible. Régénérer un prompt allégé pour Tier 2.
- **Pas de coordination model-switching** : si `interpreter` (4b) et `narrator` (9b) sont appelés sur le même tour sans cleanup, Ollama peut charger les 2 en mémoire → OOM sur M3 Pro 18 GB.
- **Pas de truncation du contexte narrateur** ([ai/narrator.py:117](ai/narrator.py)) : campagnes longues blow le context window → JSON tronqué silencieusement.

### Persistance & mémoire

- `memory/summarizer.py:53-58` : `should_summarize()` non-atomique → double-summarization possible.
- `memory/semantic.py:26` : ChromaDB sur **path global hardcodé** — leakage potentiel entre campagnes si collision d'ID.
- `db/models.py` : colonnes JSON typées `Mapped[list]` / `Mapped[dict]` sans paramètre de type → drift de schéma non détecté.
- `bot/game_session.py:94` : `action_lock` **sans timeout** → un joueur banni peut hanger toute la session.

### Discord UX

- `bot/views/equip_select_view.py` + `potion_select_view.py` : **code mort** — vues complètes, jamais instanciées. `CombatActionView` a les boutons mais ne route pas vers les vues.
- `bot/views/combat_action_view.py:62` : `timeout=None` mais fallback dépend de `TurnManager` qui peut crash → **memory leak** des vues persistantes.
- **Strings français hardcodés partout** alors que `bot/i18n.py` (220 LoC) existe et est sous-utilisé.
- `bot/views/base.py:32-35` : `on_error` envoie "Une erreur est survenue" sans détail, sans ref d'erreur.
- `bot/cogs/session.py:175-182` : `except Exception` large autour de la création de campagne — DB pas rollback si channel-creation échoue.

## P2 — Refactors architecturaux

### Splits prioritaires

- **[bot/combat_turn_manager.py](bot/combat_turn_manager.py) (827 LoC)** mélange : orchestration, NPC brain dispatch, exécution attaque, rendu dés, lifecycle hub message, persistance, timeouts, hydratation scene. **Split suggéré** :
  - `NPCTurnResolver` (logique tier minion/elite/boss)
  - `PCTurnPrompt` (prompt + view + timeout)
  - `TurnHubMessage` (lifecycle Discord message)
  - callback de persistance externalisé

- **[bot/scene_hydration.py](bot/scene_hydration.py) (700 LoC)** mélange : NPC tier resolution, description narrateur combat/exploration, raisonnement zone/location, query inventaire. **Split** :
  - `CombatSceneDescriber`
  - `bot/npc_hydration.py`
  - `LocationContextBuilder`

- **[bot/pipeline/resolve.py](bot/pipeline/resolve.py)** : `resolve_flee` modifie la location dans le pipeline d'action — viole la séparation pipeline (interpret + narrate) vs orchestration (turn). À sortir.

### Discipline Pydantic

- Spec `db/models.py` colonnes JSON avec types stricts (`Mapped[list[str]]` au lieu de `Mapped[list]`).
- Tous les `.model_validate()` côté `db/mappers.py` doivent être wrappés en `try/except ValidationError` avec log + fallback.
- `memory/models.py:115` : `metadata: dict[str, str]` mais indexer convertit int→str → typer un wrapper `MetadataValue` ou exposer un helper.

### Tokens & contexte

- Remplacer `memory/token_utils.py` par `tiktoken` (ou équivalent Qwen) pour estimation précise.
- `memory/context_assembler.py:132-166` : ajouter `max_iterations` au loop de truncation pour éviter le spin.
- Documenter explicitement l'ordre de drop : RAG > summaries > sliding > state (state immuable).

### Concurrency

- `bot/game_session.py` : timeout sur `action_lock` (ex. 60s) + cleanup sur disconnect.
- Per-guild lock au niveau du repository pour SQLite (writes concurrents entre guilds).
- ChromaDB path par guild ou par campaign (pas global).

## Mes 5 recommandations prioritaires (impact / effort)

1. **Fix C1 (`/end_campaign` host check)** — 10 minutes, fixe un exploit user-facing.
2. **Fix C3 + C4 ensemble** (lock combat + assertion `is_alive` après `advance_turn`) — la race sur turn order est un bug latent qui va casser des sessions live aléatoirement.
3. **Fix C2 (auto-crit unconscious)** — règle D&D fondamentale, joueurs vont le remarquer.
4. **Refactor `combat_turn_manager.py`** en 3-4 modules — sans ça, chaque feature combat suivante devient plus risquée. C'est le plus gros chantier mais débloque le reste.
5. **Migrer `token_utils.py` vers `tiktoken`** + ajouter cap de safety dans `context_assembler` — silently truncated context = bugs narratifs invisibles, source de frustration.

## Observations architecturales positives

- **Frontière LLM/engine sainte** (Audit #1) : aucune import de `ai/` dans `engine/`, aucun `random.*` dans `ai/`, le 6-step pipeline est respecté.
- **Beat progression engine** bien designé : 3-state (ADVANCE / STAY / NEEDS_JUDGE) avec LLM seulement sur ~20 % des tours.
- **Sanitization arc generator** : prompt + fallback Python (`_ensure_boss_defeat_objective`) garantit la jouabilité même si LLM hallucine.
- **BeatJudge** : whitelist des objectives IDs côté code (anti-hallucination) — bonne pattern à généraliser.
- **138 fichiers de tests** pour ~17.5k LoC — coverage solide.
